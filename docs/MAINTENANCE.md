# Maintaining reusable CCS knowledge

This is a casebook updated during authorized development tasks, not a background
monitor or an automatic editor of every adopting project.

## Promote one lesson

1. Identify a concrete surprise, failed assumption or repeated resource cost.
2. Keep raw operational evidence in its project. Prepare an anonymized case with
   only the transferable mechanism and necessary aggregate measurements.
3. Classify claims: observed, inferred, proposed, validated, superseded. State the
   validation platform and remaining uncertainty.
4. Add the case, its index entry, a narrow rule/template correction and CHANGELOG
   in one task branch/PR. Reuse a current matching PR for corrections.
5. Check links, whitespace and publication scope before publishing. Review the
   complete public file inventory; a token-pattern scan alone cannot prove privacy.
6. After acceptance, explicitly adopt the applicable rule into each project that
   needs it. Record the CCS revision/path there; leave its local constraints intact.

A useful case is short enough to reuse and precise enough not to become folklore.
Do not add universal rules from one unexplained failure. Preserve a corrected
hypothesis when it explains why an attractive workaround was rejected.

## Authority and updates

An adopting project's explicit user task and local invariants govern that project.
Upstream CCS changes are proposals until adopted. Link or vendor the chosen version;
do not require a live network fetch to understand a task. Keep the project's
WORKFLOW, handoff and specific reports beside its source.

Only an active authorized task can publish a new case. If public release of a
particular fact is unclear, omit/generalize it and record the gap privately.
